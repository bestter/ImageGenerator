💡 **What:** Attempted to optimize the initial capacity of `List<GenerationHistoryModel>` when filtering the history cache by setting the capacity to `_allHistoryCache.Count`.

🎯 **Why:** The hypothesis was that avoiding reallocation during the population of the list would improve performance and reduce GC overhead.

📊 **Measured Improvement:** No meaningful performance improvement was found, and in fact, memory allocations increased significantly.

*   **Benchmark Baseline:**
    *   No capacity initialized: ~283M ticks, ~328KB allocations.
*   **With Change:**
    *   Capacity initialized to source list count: ~282M ticks, ~80MB allocations.

**Rationale for Degradation:**
Initializing the `List<T>` capacity to the size of the *entire* source collection when creating a *filtered subset* causes massive memory over-allocation when the subset is small. This creates a 80MB array under the hood instead of a dynamic array that grows as needed. Given that the search results are typically much smaller than the full history cache (especially as the user types more of the query), dynamically growing the list causes far less GC pressure than pre-allocating an enormous empty array.

Therefore, this "optimization" is actually a degradation and the PR documents this finding.
